# Customer-service operations case study

A reproducible synthetic reporting extension to the enquiry-desk CRM. All 120 enquiries are fictional and generated by build.py; timestamps and service patterns are designed fixtures, not measured performance. There are no customer identifiers or real messages. This is an analytical companion, not a live integration with CRM records.

![Computed fictional workload](workload.svg)

## Reproduce

Run `python operations/build.py` from the repository root, using Python 3.11+. Only the standard library is required. The script validates keys, timestamp order and independently reconciles the mean first-response calculation. Outputs: enquiries.csv, channel_summary.csv, metrics.json and workload.svg. Snapshot: 31 October 2026 at 00:00, timezone-naive fixture timestamps. The SQLite database is in memory.

## Business question and definitions

Where is the open queue concentrated, and which enquiries need follow-up? One row is one enquiry. Backlog means no resolution timestamp at the snapshot; unanswered means no first reply. Response and resolution use elapsed calendar hours, not staffed business hours. Mean response excludes unanswered records, so always display its coverage alongside it. A resolved record is not proof of customer satisfaction. See metrics.sql for executable calculations.

## Findings and proposed action

The fixture contains 120 enquiries, 30 open and 18 without a first response. Each channel has 40 enquiries and 10 open: this deliberate balance provides a reconciliation check, not evidence that real channels behave alike. Review unanswered and older open enquiries first; compare future snapshots before proposing staffing changes. Category assignment and closure are deliberately related by the generator, so category differences must not be interpreted as empirical effects.

## Process and requirements

Current prototype: capture enquiry → suggest exact-match reply → save CRM record → human review → status update. Proposed reporting process: export timestamped events → validate → compute queue metrics → review exceptions → assign follow-up → review the next snapshot. Human reviewers approve responses and closure.

| Requirement | Acceptance criterion |
|---|---|
| Show workload | Total, open and unanswered counts reconcile to row-level CSV |
| Explain speed | Response-time card includes answered denominator and calendar-hours label |
| Prioritise follow-up | Open enquiries older than 48 hours are counted at the stated snapshot |
| Protect information | Demo uses fictional records only; no emails or enquiry text exported |
| Prevent misleading comparisons | Report states synthetic provenance and active filters |

The 48-hour threshold is a demonstration rule, not a contractual SLA. Suggested success measures for a real pilot are backlog age, unanswered proportion, response coverage and reopened enquiries; no improvements or savings are claimed.

## Power BI implementation guide

Import enquiries.csv with Text/CSV; set the ID to whole number and the three timestamp fields to Date/Time. Use a star model for expanded data: a fact table at enquiry grain with channel, category and date dimensions. For this single-table fixture, no joins are needed. Add channel/category slicers, total/open/unanswered cards, an open-queue table and a channel workload chart. All counts must match metrics.json with filters cleared. Recalculate averages for the selected rows rather than averaging channel averages. Use a fixed snapshot parameter for age calculations; never silently substitute today's date.

A native PBIX dashboard has not been authored or validated for this extension. The SVG is a reproducibly generated chart, not a Power BI screenshot. The CSV, SQL and definitions are ready for building and checking that report.
